# WorkoutTracker v2.0.0 Master Roadmap

## Status
Planned

## Release theme
**Smarter recovery, better workout structure, clearer progress.**

WorkoutTracker v2.0.0 should deepen the core workout loop rather than broaden the app with loosely related features. The release should improve:

- what happens during the workout
- how routines are structured
- how progress is understood over time
- how safe and polished the app feels to ship

---

# 1. Approved scope

## Required scope
- Rest Timer 2.0
- Linked warm-up / cool-down routines
- Progress Hub v1
- Full i18n foundation + one additional language
- Focused test hardening

## Optional scope
- Calories count

## Explicitly out of scope for v2.0.0 unless something becomes nearly free
- General calorie estimation for strength training
- Advanced coaching/recommendation engine
- Large chart-heavy dashboard
- Deep routine graph authoring
- Multiple warm-up or cool-down chains
- Major unrelated redesigns
- Broad watch-only feature expansion not required by regressions

---

# 2. Product goals

## Primary goals
1. Make rest handling more useful without adding complexity.
2. Let routines include warm-up and cool-down structure cleanly.
3. Give users meaningful progress insight, not vanity charts.
4. Make the app truly localization-ready and ship a second language.
5. Improve confidence in the release with focused testing and stabilization.

## Non-goals
1. Turn the app into a full coaching platform.
2. Add speculative analytics with weak data quality.
3. Introduce broad persistence complexity unless clearly necessary.
4. Rewrite major existing systems unless additive evolution is insufficient.

---

# 3. Architecture principles

## 3.1 Keep business logic out of views
Logic for:
- rest timer transitions
- linked routine planning
- analytics calculations
- optional calorie data mapping

should live in services/helpers, not SwiftUI view bodies.

## 3.2 Prefer additive model changes
v2 should extend the current app model with optional links, optional metadata, and new derived services instead of rewriting core data structures.

## 3.3 Analytics should be derived first
Progress analytics should be computed from workout history and session data. Do not introduce a large persisted analytics cache in v2 unless performance proves it is necessary.

## 3.4 Warm-up and cool-down must stay distinguishable
Main workout work should remain distinguishable from warm-up/cool-down work so Progress Hub can avoid polluting strength-related signals.

## 3.5 Localization is infrastructure, not polish
Localization support should be introduced early and then completed later, rather than treated as a last-minute text replacement pass.

## 3.6 UI-test seed/setup must live in UITestHost
Any UI-test seeding, launch configuration, or fail-fast validation must live under:

- `workouttrackerUITestHost/**`

not under the main app target.

# 7. Dependency map

## Foundational dependencies
- Localization foundation should exist before broad v2 UI work is finalized.
- Rest timer engine should exist before timer UI polish.
- Linked routine model must exist before routine editor and session segment flow.
- Session segment flow should exist before Progress analytics finalize filtering rules.
- Analytics service outputs should exist before Progress UI.
- Full localization pass should happen after v2 feature copy stabilizes.
- Final stabilization should happen after localization and UI surfaces are mostly complete.

## Key functional dependencies
- Progress Hub depends on:
  - linked routine segment identity
  - enough workout history data to derive trends
  - rest data where available for efficiency
- Calories depends on:
  - trustworthy health/energy source
  - extremely low release risk

---

# 8. SwiftData / migration strategy

## Principles
- additive optional fields only whenever possible
- old data must remain valid
- no destructive migration
- no large backfill requirements for v2

## Likely migration touchpoints
- routine model:
  - optional warm-up routine link
  - optional cool-down routine link
- session/log models:
  - segment kind
  - optional rest metadata only where clearly needed
- schema definition file
- migration plan file

## Compatibility expectations
- existing routines without links continue working
- older sessions without extra v2 metadata remain readable
- Progress Hub degrades gracefully when older data is incomplete

- `SessionRestTimerUITests`

- `workouttrackerUITestHost/workouttrackerUITestHostApp.swift`

# 11. Optional calories decision framework

## Default recommendation
Defer calories to **v2.0.1** unless it is already close and trustworthy.

## Include calories in v2.0.0 only if all are true
- data source is trustworthy
- scope remains narrow
- UI remains small
- testing burden is small
- release risk remains low

## Safe v2 calories scope if included
- cardio-oriented energy summaries only
- preferably HealthKit / Apple Watch sourced
- clearly labeled source
- no generalized calorie estimation for lifting

# 12. Major risks and mitigations

## Risk: v2 becomes too broad
### Mitigation
- keep optional calories truly optional
- do not expand routine linking beyond one warm-up and one cool-down
- avoid advanced analytics clutter

## Risk: analytics become hard to trust
### Mitigation
- derive from normalized samples
- keep low-data states explicit
- separate calculators from UI

## Risk: localization becomes last-minute churn
### Mitigation
- establish infrastructure first
- keep using localized strings during feature development
- do full rollout after copy stabilizes

## Risk: UI tests become brittle
### Mitigation
- seed only through UITestHost
- fail fast on missing seeded data
- follow existing suite interaction patterns

## Risk: migration complexity grows late
### Mitigation
- additive optional migrations only
- do model changes in earlier dedicated PRs
- avoid late persistence changes in stabilization

# 14. Manual verification checklist for release candidate

## Sessions
- start a session
- complete a set
- rest timer appears
- timer reaches zero and remains useful
- quick extend works
- next action clears/resolves timer correctly

## Linked routines
- edit a routine and attach warm-up
- attach cool-down
- start linked flow
- skip warm-up
- finish main and enter cool-down
- skip cool-down
- no-linked-routine flow still works normally

## Progress
- open Progress
- strength card shows data where expected
- volume card shows data where expected
- consistency card shows data where expected
- recovery card handles partial/no data honestly
- open exercise detail
- low-data states do not look broken

## Localization
- launch in Spanish
- session labels/buttons are localized
- routine linking labels are localized
- Progress labels are localized
- no obvious layout breakage in main device classes

## Migration
- open with older data
- older routines still load
- older history still loads
- Progress does not misrepresent incomplete legacy data

## Optional calories
- only if included:
  - energy data appears only where supported
  - source labeling is clear
  - no unsupported exercise types pretend to have calories

# 16. Final recommendation

For v2.0.0, keep the release identity tight:

**WorkoutTracker 2.0.0 makes the app smarter during workouts, more structured before and after workouts, and more useful when reviewing progress.**

If scope pressure appears, cut in this order:
1. calories
2. advanced Progress visuals
3. extra non-essential localization polish beyond the core v2 flows

Do not cut:
- Rest Timer 2.0
- linked warm-up/cool-down support
- Progress analytics core
- Progress dashboard core
- localization foundation
- focused test hardening

Those are the bones of the release.
