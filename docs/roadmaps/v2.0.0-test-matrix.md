# WorkoutTracker v2.0.0 Test Matrix

## Status
Planned

## Purpose
This document defines the **test coverage map** for WorkoutTracker v2.0.0.

It is the execution companion to:

- `docs/roadmaps/v2.0.0-master-roadmap.md`
- `docs/roadmaps/v2.0.0-release-checklist.md`

Use it to answer:

- what must be tested
- where each test should live
- which areas need unit tests vs UI smoke tests
- what seeded data is required
- what must pass before v2.0.0 is release-candidate ready

---

# 1. Testing principles for v2.0.0

## 1.1 Focus on risk, not raw coverage %
The goal is not to maximize total test percentage.

The goal is to protect the parts of the app most likely to regress because of v2:

- session flow
- rest timer behavior
- linked warm-up/cool-down flow
- analytics correctness
- Progress UI
- localization smoke coverage

---

## 1.2 Prefer unit tests for logic, UI tests for critical user flows
### Unit tests should own:
- timer state transitions
- routine link validation/planning
- analytics math
- view-model mapping logic
- localization/formatting helpers

### UI tests should own:
- “can the user complete the flow?”
- “does the seeded scenario render correctly?”
- “does navigation still work across the release-critical paths?”

---

## 1.3 UI-test seed/setup must live under UITestHost
For WorkoutTracker, any UI-test seeding, launch-time validation, or fail-fast assertion must be implemented under:

- `workouttrackerUITestHost/**`

not under the main app target.

That means seeded assumptions for:
- rest timer scenarios
- linked warm-up/cool-down routines
- Progress history
- localization launch scenarios

must all be created and validated in the UITestHost.

---

## 1.4 Seeded assumptions must fail fast
If a UI test depends on seeded data, add a `UITESTS_SEED` gated assertion in the UITestHost that crashes with a clear message when expected data is missing.

This is especially important for:

- `SessionRestTimerUITests`
- `RoutineLinkedFlowUITests`
- `ProgressHubUITests`
- `LocalizationSmokeUITests` when they depend on seeded content

# 3. Test areas by feature

---

## 3.1 Localization foundation

### Goal
Verify localization infrastructure and formatting helpers are correct and reusable.

### Unit tests
**Target:** `workouttrackerTests/`

**Recommended file:**
- `workouttrackerTests/Support/Localization/AppFormattingTests.swift`

### What should be tested
- duration formatting
- minute/second boundaries
- date formatting returns locale-safe output
- time formatting returns locale-safe output
- decimal/number formatting behaves predictably
- future helper functions used by Progress cards/detail

### UI smoke
**Target:** `workouttrackerUITests/`

**Recommended file:**
- `workouttrackerUITests/LocalizationSmokeUITests.swift`

### What should be tested
- app launches in second language
- key v2 screens show localized labels
- obvious truncation/regression is not present on core flows

### Seed requirements
**Target:** `workouttrackerUITestHost/`

Needed if localization tests navigate into:
- Progress
- routine editor/detail
- active session flow

---

## 3.2 Rest Timer 2.0

### Goal
Protect the new recovery-aware rest behavior.

### Unit tests
**Target:** `workouttrackerTests/`

**Recommended file:**
- `workouttrackerTests/Services/Sessions/RestTimerEngineTests.swift`

### What should be tested
- start countdown with valid planned rest
- snapshot before zero
- snapshot exactly at zero
- overdue state after zero
- extend by 15/30/60 seconds
- extend while already overdue
- resolve/clear on next action
- completion cue fires once
- zero/invalid planned rest degrades safely
- inactive state behaves predictably

### UI smoke
**Target:** `workouttrackerUITests/`

**Recommended file:**
- `workouttrackerUITests/SessionRestTimerUITests.swift`

### What should be tested
- completing a set shows the timer
- timer remains visible after zero
- overdue state is visible
- `+15s`, `+30s`, `+60s` work
- next workout action clears/resolves timer
- layout remains acceptable in seeded scenario

### Seed requirements
**Target:** `workouttrackerUITestHost/`

Needed seeded data:
- deterministic active session
- deterministic routine/exercise/set state
- fail-fast assertion that seeded session exists

---

## 3.3 Linked warm-up / cool-down routines

### Goal
Protect new routine linking and segment-aware session flow.

### Unit tests
**Target:** `workouttrackerTests/`

**Recommended files:**
- `workouttrackerTests/Services/Workouts/RoutineLinkPlannerTests.swift`
- `workouttrackerTests/Services/Workouts/RoutineEditingBehaviorTests.swift` (extended)

### What should be tested
#### Planner / validation
- no linked routines
- warm-up only
- cool-down only
- both linked
- self-link rejection
- simple cycle rejection if supported
- execution order is always warm-up → main → cool-down

#### Editing behavior
- attach warm-up
- attach cool-down
- replace linked routine
- remove linked routine
- existing routine items remain intact

### UI smoke
**Target:** `workouttrackerUITests/`

**Recommended file:**
- `workouttrackerUITests/RoutineLinkedFlowUITests.swift`

### What should be tested
- routine editor can show linked-routine UI
- starting a linked routine enters warm-up
- skip warm-up works
- segment header changes to main
- finishing main enters cool-down
- skip cool-down works
- session finishes successfully
- no-linked-routine flow still works

### Seed requirements
**Target:** `workouttrackerUITestHost/`

Needed seeded data:
- warm-up routine
- main routine linked to warm-up and cool-down
- cool-down routine
- fail-fast assertions that links exist and are valid

---

## 3.4 Analytics engine

### Goal
Protect correctness of the Progress math.

### Unit tests
**Target:** `workouttrackerTests/`

**Recommended files:**
- `workouttrackerTests/Services/Analytics/PersonalRecordCalculatorTests.swift`
- `workouttrackerTests/Services/Analytics/WeeklyVolumeCalculatorTests.swift`
- `workouttrackerTests/Services/Analytics/ConsistencyCalculatorTests.swift`
- `workouttrackerTests/Services/Analytics/SessionEfficiencyCalculatorTests.swift`
- `workouttrackerTests/Services/Analytics/ProgressAnalyticsServiceTests.swift`

### What should be tested

#### PersonalRecordCalculator
- best weight
- best reps
- estimated 1RM where appropriate
- incomplete data ignored
- warm-up/cool-down excluded from core progression
- ties handled safely
- insufficient data state

#### WeeklyVolumeCalculator
- weekly grouping
- total sets
- total reps
- total load/tonnage
- multi-week rollups
- exercise trend summary
- main-only filtering for core progression summaries

#### ConsistencyCalculator
- workouts/week
- active weeks
- completion rate where supported
- partial session history
- low-data windows

#### SessionEfficiencyCalculator
- planned vs actual rest
- average overrun
- partial/no rest data
- exercises with highest overrun
- graceful degradation when metadata is incomplete

#### ProgressAnalyticsService
- dashboard summary with full data
- dashboard summary with partial data
- exercise detail summary
- missing efficiency data still produces valid output
- filtering logic is consistent with segment rules

### Test data style recommendation
Use normalized sample builders instead of raw persistence models wherever possible.

That keeps these tests small, fast, and focused on logic.

1. `RestTimerEngineTests`

3. `PersonalRecordCalculatorTests`
4. `WeeklyVolumeCalculatorTests`
5. `ProgressAnalyticsServiceTests`
6. `ConsistencyCalculatorTests`

# 8. Seeded scenario definitions

These are the seeded scenarios I would standardize in `workouttrackerUITestHost/`.

## Scenario A — Active rest timer session
Used by:
- `SessionRestTimerUITests`

Should contain:
- one active session
- enough state to complete a set and show the timer
- predictable exercise/set labels

Fail-fast check:
- crash with clear message if active session or target set is missing

---

## Scenario B — Linked routine flow
Used by:
- `RoutineLinkedFlowUITests`

Should contain:
- warm-up routine
- main routine
- cool-down routine
- correct linking between them
- predictable routine names

Fail-fast check:
- crash with clear message if routines or links are missing

---

## Scenario C — Rich progress history
Used by:
- `ProgressHubUITests`

Should contain:
- one or more exercises with enough main-segment history for PRs
- multiple weeks of history for volume
- enough completed sessions for consistency
- rest metadata if available for efficiency

Fail-fast check:
- crash with clear message if history is insufficient for expected dashboard assertions

---

## Scenario D — Low-data progress history
Used by:
- `ProgressHubUITests` optionally
- `LocalizationSmokeUITests` optionally

Should contain:
- minimal history
- enough to open Progress
- not enough to show every card fully

Fail-fast check:
- crash with clear message if the low-data scenario accidentally becomes empty or over-seeded

---

## Scenario E — Localization launch
Used by:
- `LocalizationSmokeUITests`

Should contain:
- locale launch arguments
- optional seeded routine/history for navigation if needed

Fail-fast check:
- only if dependent seeded content is required

# 9. Pass/fail guidance

## A test matrix row is considered complete when:
- the test file exists
- the intended scenario is covered
- the assertions are stable and meaningful
- any required seed exists in UITestHost
- the test is not depending on accidental data or manual preconditions

## A feature area is considered sufficiently covered when:
- domain logic has unit coverage where it contains real branching/math
- one or more focused UI smoke tests protect the critical user flow
- low-data states are tested where important
- seeded assumptions are validated explicitly

# 11. Test failure triage guidance

## If a unit test fails
Check:
1. did business rules change intentionally?
2. is the normalized analytics/sample builder stale?
3. did segment filtering assumptions change?
4. is low-data behavior now different by design?

## If a UI test fails
Check:
1. did the seeded data change?
2. did accessibility identifiers/labels change?
3. did navigation structure change?
4. is the failure due to layout timing or actual behavior?
5. does the UITestHost fail-fast assertion still reflect current assumptions?

## Required artifacts for UI-test debugging
When a UI test fails, gather:
- the current failing test file(s) under `workouttrackerUITests/**`
- the relevant `workouttrackerUITestHost/**` files
- the screenshot attachment from the failing run
- the accessibility hierarchy attachment from the failing run

This is especially important for Progress and linked-routine flows.

# 13. Summary

WorkoutTracker v2.0.0 test coverage should be shaped around **release risk**, not raw quantity.

The highest-priority protections are:

1. rest timer behavior
2. linked routine/session flow behavior
3. analytics correctness
4. Progress feature rendering and drill-down
5. localization smoke coverage
6. deterministic UI-test seeding through UITestHost

If time pressure forces tradeoffs:
- keep the unit coverage for core logic
- keep the 4 main UI smoke suites
- cut lower-value expansions before cutting these protections
